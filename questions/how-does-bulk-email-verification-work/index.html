How does bulk email verification work?批量邮箱验证是怎么工作的？

SHORT ANSWER短答

In three steps. First the list goes in — pasted, uploaded as a file, or sent to a batch API endpoint. Then every address runs the same pipeline a single check uses: syntax, domain and DNS records, MX routing, disposable and role-account signals, typo detection, domain age and catch-all risk, combined into a 0–100 score and a verdict. Finally the scored rows come back in order, with summary counts, and you segment: send to the valid rows, fix or quarantine the risky ones, delete the invalid ones. No email is sent to the addresses, and no mailbox is probed at any step.

三步。第一步，名单进来——粘贴、上传文件，或发给批量 API 端点。第二步，每个地址跑和单查相同的流水线：格式、域名与 DNS 记录、MX 路由、一次性与角色账号信号、拼写检测、域名年龄、catch-all 风险，合成 0–100 分和裁决。第三步，带分数的结果按原顺序返回、附汇总计数，你据此分段：valid 的发、risky 的修或隔离、invalid 的删。整个过程不给这些地址发信，任何一步都不探测邮箱。

Step 1: the list goes in第一步：名单进来

Input is deliberately boring: one address per line, a CSV or TXT upload, or a JSON array to a batch endpoint. EmailCheck's batch endpoint takes up to 100 addresses per call, so longer lists are split into chunks of 100 — the results are identical either way. Two properties matter at this step. Empty lines are skipped rather than treated as entries. And a malformed row marks only itself invalid; it never fails the batch, because real-world lists always contain a few broken rows and a run that dies on row 37 is useless.

输入环节故意做得无聊：一行一个地址、上传 CSV 或 TXT、或把 JSON 数组发给批量端点。EmailCheck 的批量端点每次调用最多 100 条，更长的名单按每 100 条分片——结果没有区别。这一步有两个性质要紧：空行直接跳过、不当条目；格式坏的行只把自己标成 invalid，绝不连坐整批——真实名单里总有几行是烂的，一跑到第 37 行就死的工具没法用。

Step 2: every address runs the same pipeline第二步：每个地址跑同一条流水线

Each address passes through the checks in a fixed order. Syntax first — is it shaped like an address at all. Then the domain: does it exist, and does it publish MX records that accept mail. Then the signal layer: disposable-domain lists, role-account patterns, typo detection against major providers (with the corrected address suggested), domain age from RDAP registration records, and a catch-all risk signal inferred from MX and provider patterns. The score starts at 100 and is reduced for each signal that fires; the verdict bands are valid (80–100), risky (50–79) and invalid (below 50). Every lookup is a DNS or registry query — nothing connects to a mail server, and nothing is sent.

每个地址按固定顺序过检查。先是格式——它到底像不像一个地址。然后是域名：存不存在、有没有发布接受邮件的 MX 记录。再是信号层：一次性域名名单、角色账号模式、对主流服务商的拼写错误检测（并给出纠正后的地址）、来自 RDAP 注册记录的域名年龄、以及由 MX 与服务商模式推断的 catch-all 风险信号。分数从 100 起、每触发一个信号扣分；裁决分段为 valid（80–100）、risky（50–79）、invalid（50 以下）。所有查询都是 DNS 或注册记录查询——不连接邮件服务器，也不发送任何东西。

Step 3: scored rows come back, and you segment第三步：带分数的结果回来，你做分段

The output is rows in submission order — address, verdict, score, and the reasons — plus a summary: totals per verdict, disposable count, likely-typo count. Segmentation is the actual work the run enables. Valid rows go into the send. Risky rows get split by reason: apply typo corrections and re-check them, hold catch-all-risk addresses for a smaller, monitored send, drop disposables from anything but a first touch. Invalid rows are deleted, not retried. The bulk email checker shows this output shape on a real run, and how accurate bulk verification is covers what the bands can and cannot promise.

输出是按提交顺序排列的行——地址、裁决、分数、原因——外加汇总：各裁决的总数、一次性域名计数、疑似拼写计数。分段才是这一轮真正让你能干的活：valid 行进发送；risky 行按原因拆——有拼写纠正的改完重验，catch-all 风险的留给小批量、盯着退信的发送，一次性域名的除了第一次触达都去掉；invalid 行删除、不重试。批量检查器里能看到一次真实运行的输出长什么样，批量验证到底有多准讲了这些分段能承诺什么、不能承诺什么。
