Can you verify an email address without sending an email?不发邮件，能验证一个邮箱地址吗？

SHORT ANSWER短答

Yes — almost everything about an address can be verified without sending anything: that it is well-formed, that the domain exists and accepts mail, that it is not a disposable or role address, that the domain is not a typo of a major provider, and how risky the domain's catch-all behaviour makes it. The one thing that cannot be established without sending is that a specific mailbox exists and is read — and even sending only half-proves that, because catch-all domains accept mail for addresses that do not exist. Verification without sending is not a lesser substitute; for list hygiene it is the correct tool, because sending test mail to a cold list damages the sender reputation you were trying to protect.

能——关于一个地址的几乎一切，都不用发信就能验证：格式是否正确、域名是否存在并收信、是不是一次性或角色地址、域名是不是主流服务商的拼写错误、以及域名的 catch-all 行为带来多大风险。唯一不发信无法确立的是：某个具体邮箱存在并且有人读——而且就算发了也只证明一半，因为 catch-all 域名会替不存在的地址收信。不发信的验证不是将就的替代品；对名单清洗来说它才是对的工具，因为给冷名单发测试信，伤的正是你想保护的发信声誉。

Everything that works without sending不发信就能做的一切

The full domain-level stack runs on lookups, not messages. Format validation is local. Domain existence and MX routing are DNS queries — the same records a mail server would consult to deliver your message. Disposable and role-account detection is pattern and list matching. Typo detection compares the domain against major providers. Domain age comes from registration records. Catch-all risk is inferred from MX and provider patterns and returned as a labelled signal. Put together — as the verify email address checker does — that is enough to sort addresses into valid, risky and invalid with the evidence shown, which is the decision list hygiene actually needs.

整套域名级检查跑的是查询，不是发信。格式校验在本地完成；域名存在与 MX 路由是 DNS 查询——正是邮件服务器投递前要查的同一批记录；一次性与角色账号检测是模式与名单匹配；拼写检测是把域名和主流服务商比对；域名年龄来自注册记录；catch-all 风险由 MX 与服务商模式推断、并以信号形式明示返回。合在一起——就像验证邮箱地址检查器做的——足够把地址分成 valid、risky、invalid 并附证据，而这正是名单清洗需要的决策。

The one thing that does not work唯一做不到的那件事

Confirming an individual mailbox. The protocol route — connecting over SMTP and asking the server whether it would accept mail for that user — is rejected or greylisted by major providers precisely because verifiers abused it, and on catch-all domains the server answers “yes” for every name anyway. So mailbox confirmation is not a feature honest tools sell. What they can sell is everything around it: if the domain is real, routes mail, is not disposable, and the address is well-formed, the remaining uncertainty is narrow and known. The detailed version of this boundary is in does email verification check if a mailbox exists.

确认某个具体邮箱。协议路线——走 SMTP 连上去问服务器接不接这个用户的信——会被主流服务商拒绝或灰名单处理，原因正是验证工具滥用过它；而且在 catch-all 域名上，服务器对任何名字都答「收」。所以「确认邮箱」不是诚实工具会卖的功能。能卖的是它周围的一切：域名是真的、能路由邮件、不是一次性的、地址格式正确——剩下的不确定性就既窄又已知了。这个边界的详细版在邮箱验证到底查不查邮箱存在。

Why not just send a test email?为什么不干脆发一封测试信？

Three reasons. It does not prove what you want: on a catch-all domain the test mail is accepted for a nonexistent address, and a real mailbox that ignores you looks identical to a dead one — silence is not data. It costs the thing you are protecting: hard bounces from a test send count against your sender reputation exactly like bounces from a real send, because to the receiving provider they are the same event. And it spends the contact: a “just testing” message to a customer or lead is a real impression you cannot take back. Verify first, without sending; then let the real send — to the verified segment, in order — be the only mail those addresses ever get from you.

三个原因。它证明不了你想证明的：catch-all 域名会替不存在的地址收下测试信，而一个不理你的真邮箱和死邮箱看起来一模一样——沉默不是数据。它消耗的正是你在保护的东西：测试发送的硬退信和真实发送的退信，在接收方眼里是同一件事、同样记在你的发信声誉上。它还会花掉这次触达：给客户或线索发的「只是测试」是一次收不回的真实曝光。先验证、不发信；然后让真正的那封信——发给验过的分段、按顺序发——成为这些地址从你这儿收到的唯一邮件。
